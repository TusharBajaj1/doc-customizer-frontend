# Languages (translations)

English is the default and lives at the site root (`/tools/split`). Every other language lives under its code (`/hi/tools/split`).
Every page has a **language button** in the header (globe icon + the current language) that opens a list of the available languages.

## Which languages exist, and which ones Google may list
There are two separate settings, both optional:

| Setting (Vercel environment variable) | Default | Meaning |
|---|---|---|
| `NEXT_PUBLIC_LOCALES` | `en,hi,es,pt` | Languages **visitors can use** (they appear in the language button). Supported codes: `en hi es pt bn ta te mr ur ar`. |
| `NEXT_PUBLIC_INDEXED_LOCALES` | `en` | Languages **search engines may list**. A language not in this list still works for visitors but its pages are marked `noindex` and left out of the sitemap and `hreflang` tags. |

Why two settings: while a language is only partly translated, mixed-language pages can hurt search ranking, so they are hidden from Google
but fully usable. When a language is complete and reviewed, add it to `NEXT_PUBLIC_INDEXED_LOCALES` (e.g. `en,hi`) and redeploy: it gets
indexable pages, sitemap entries and `hreflang` links automatically.
Other automatic extras per language: `<html lang dir>` and right-to-left direction for Urdu/Arabic. Unknown or disabled codes return 404.
The Android app is built English-only (`APP_LOCALES=en,hi npm run build:app` to include more), so it shows no language button for now.

### Guides are per-language and opt-in
Guide articles are long, so a language only gets guide pages **once its guides are translated** (`messages/<lang>.guides.json` has entries).
Until then that language has no guide URLs, no guide links in its menu/footer/tool pages, no guide entries in the sitemap, and no guide
`hreflang` alternates; the language button sends a visitor on a guide page to that language's home page rather than to a 404.
English guides are unaffected. Adding guide translations for a language switches all of this on automatically.

## How text is translated
The **English text is the key.** `messages/<lang>.json` maps an English string to its translation:
```json
{ "Merge PDFs": "PDF मर्ज करें", "All {n} tools": "सभी {n} टूल" }
```
- If a translation is missing the English shows, so a half-translated language still works (it just looks mixed).
- `{name}` placeholders must appear unchanged in the translation (`{n}`, `{site}`).
- `messages/<lang>.guides.json` holds the long guide articles (loaded only on guide pages). `messages/<lang>.json` holds everything else.
- Don't translate the brand name PDFRookie, file names/extensions (PDF, DOCX), or the placeholders.

## Workflow
```bash
npm run i18n:extract        # refresh messages/en.json and messages/en.guides.json from the source
npm run i18n:status         # coverage per language + checks for broken placeholders / stray markup
```
1. Run `i18n:extract` after the English text changes. Stale or new keys show up in `i18n:status`.
2. Translate by adding entries to `messages/<lang>.json` (and `.guides.json`). Keep keys exactly as in `messages/en.json`.
3. Run `i18n:status` until it reports no problems.
4. **Get a native speaker to review** before turning the language on (see the checklist).

Current size: about 270 interface/tool strings (~2,400 words) and 392 guide strings (~5,500 words) per language.

## Review checklist for a native reviewer
- Does it read naturally, not like a literal translation? Are tool names what people actually search for in that language?
- **Privacy and safety claims** ("your files never leave your device", "files are deleted right after", cookie/analytics wording) must be exactly as accurate as the English. These matter most.
- Numbers, ranges and examples still make sense (`2, 5-7`, `1-3`).
- Buttons are short enough to fit; no broken line wrapping.
- Right-to-left languages: punctuation and mixed English/numerals read correctly.

## Status of the pilot
- Done: the translation system, routing, switcher, SEO tags, sitemap, RTL direction, scripts.
- Sample translations (unreviewed) exist for the shared interface, home page and tool names in `hi`, `es`, `pt` (about 40%).
- **Not yet translated or not yet wired to the translation system:**
  - the controls inside each tool page (buttons, labels, messages),
  - the About, Privacy and Request pages' body text (they show English in every language),
  - the guide articles (deliberately left in English for now; guides are hidden in other languages until translated),
  - the Android app's native screens and its sharing images (sharing images stay English).
- Right-to-left polish (flipping arrow icons, etc.) is still to do before Urdu/Arabic go live.

## Letting Google list a language (checklist)
Visitors can already use the languages in `NEXT_PUBLIC_LOCALES`. To also let search engines list one:
1. Translations complete for what you ship, `i18n:status` clean.
2. Native review done, especially privacy wording.
3. Add the code to `NEXT_PUBLIC_INDEXED_LOCALES` in Vercel and redeploy.
4. Check `/<lang>/` and a few tool pages; submit the updated sitemap in Search Console.
5. Watch Search Console (per-country performance) and Analytics to decide which languages deserve more guides.
